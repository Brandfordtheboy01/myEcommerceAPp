1. PROJECT OVERVIEW
================================================================================

1.1 Description
A multi-vendor e-commerce marketplace where vendors list products, fulfill orders,
and earn payouts; customers browse, purchase, and review products across vendors in
one storefront. Payments are centralized via Paystack; vendors handle delivery.

1.2 Technology Stack (current)
Component          Technology              Version / Notes
-----------------  ----------------------  ------------------------------------------
Frontend           Next.js / React         16.2.9 / 19.2.4
Backend            Supabase (PostgreSQL)   @supabase/supabase-js ^2.110
Auth               Supabase Auth           via @supabase/ssr
Payments           Paystack                v3 API + react-paystack ^6.0
Storage            Supabase Storage        product-images bucket
Hosting            Vercel                  (not yet configured)
State              Zustand                 ^5.0.3 (cart, localStorage persist)
Styling            Tailwind CSS            ^4 + shadcn/ui
Validation         Zod                     ^4.4.3
Type Safety        TypeScript              ^5

3. SYSTEM ARCHITECTURE
================================================================================

3.1 High-Level (current)
Single Next.js 16 App Router application deployed to Vercel (planned).
All data in Supabase PostgreSQL with RLS. No separate mobile or admin apps yet.

  Browser → Next.js (app/, API routes) → Supabase (PostgREST + Auth + Storage)
                                      → Paystack (payments + webhooks)

3.2 Order Processing Flow (as implemented)
  1. Customer adds items to client-side cart (Zustand)
  2. Checkout POST /api/orders — creates order + order_items (service role)
  3. Stock decremented via DB trigger on order_items insert
  4. Customer pays via Paystack (react-paystack on checkout page)
  5. Paystack webhook POST /api/webhooks/paystack
     - Validates x-paystack-signature (HMAC-SHA512)
     - charge.success → payment_status = paid, order_status = processing
     - createVendorOrdersForOrder() splits items by vendor, calculates commission
     - Updates vendor balance + vendor_transactions
  6. Vendor ships / delivers via PATCH /api/vendor/orders/[id]/status
  7. Customer views order status; can leave review on product detail

NOTE: vendor_orders are created on payment webhook, NOT on order insert.
This differs from the v1.0 plan trigger approach and is intentional.

4. DATABASE SCHEMA
================================================================================

4.1 Tables (in schema.sql)
  users, categories, vendors, coupons, products, product_images,
  carts, cart_items, wishlists, orders, vendor_orders, order_items,
  reviews, vendor_payouts, vendor_transactions

4.2 Views
  product_review_stats — average_rating, review_count per product

4.3 Storage
  Bucket: product-images (public, 5MB, jpeg/png/webp)

4.4 Key RLS Policies
  - Public read: categories, products, product_images, reviews, approved vendors
  - Users: own row only
  - Vendors: own products, vendor_orders, vendor_transactions (approved status)
  - Admins: full access via is_admin() helper

4.5 Indexes (current)
  idx_products_category, idx_products_vendor, idx_orders_user,
  idx_vendor_orders_vendor

  Missing from v1.0 plan:
  - GIN full-text search index on products
  - Composite indexes on (user_id, order_status), (vendor_id, status)

5. API ROUTES
================================================================================

5.1 Authentication
  Handled by Supabase Auth directly (signUp, signInWithPassword).
  Vendor follow-up: POST /api/vendors/register

5.2 Products
  GET  /api/products?category=&vendor=&search=
  POST /api/products (vendor-authenticated)

5.3 Orders
  POST /api/orders — cart items, shipping address, optional coupon
  Returns order + Paystack authorization_url

5.4 Payments
  Initialized inline in POST /api/orders (not separate /api/payments/initialize)
  Webhook: POST /api/webhooks/paystack

5.5 Vendor
  GET   /api/vendor/dashboard/stats
  PATCH /api/vendor/orders/[id]/status

5.6 Admin
  PATCH /api/admin/vendors/[id] — approve, reject, suspend

5.7 Post-MVP
  GET/POST /api/wishlist
  GET/POST /api/reviews
  POST     /api/coupons
  POST     /api/upload

7. PAYMENT INTEGRATION
================================================================================

7.1 Client Flow
  Checkout uses react-paystack (usePaystackPayment hook).
  Order created first via API; Paystack reference tied to order metadata.

7.2 Webhook
  Signature verified with PAYSTACK_SECRET_KEY.
  charge.success → paid + vendor order split
  charge.failed → payment_status = failed

7.3 Not Implemented
  - transfer.success for vendor payouts
  - Confirmation emails on payment
  - Periodic reconciliation of pending orders

================================================================================

8.1 Implemented
  - Row Level Security on all core tables
  - Zod validation on API inputs
  - Paystack webhook signature verification
  - Service role used only server-side for order creation and webhooks

11. FAQ
================================================================================

Q: Why are vendor_orders created on webhook, not order insert?
A: Prevents vendor earnings for unpaid orders. Commission split only runs after
   Paystack confirms payment.

Q: Why client-side cart instead of DB carts table?
A: MVP simplicity. carts/cart_items tables exist in schema for future sync.

Q: Is react-paystack compatible with React 19?
A: Installed (^6.0.0). context.md noted prior peer conflicts; currently in use
   on checkout page. Monitor for runtime issues.

Q: How do I create the first admin?
A: After signup, run in Supabase SQL:
   UPDATE users SET role = 'admin' WHERE email = 'your@email.com';

Q: What's the merge path when MVP is ready?
A: PR or merge mvp/marketplace-build → main from ecommerce/ git root.
   See context.md for exact commands.
